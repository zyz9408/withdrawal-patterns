CASE / 01
阶段任务型已分析版本 2.4

Happy Mahjong

五段任务，展示目标与实际口径分离。

关卡、有效活跃、金额、活跃日期、玩家等级依次推进；阶段完成和最终领取使用不同的执行链。

机制路径以当前已追踪流程为准
  1. 显示8关
  2. 实际40关
  3. 多段任务
  4. 玩家30级
  5. 领取缺下一流程
8 → 40显示关卡 / 实际目标

第一段显示8关，实际目标为40关。

99,99929级升30级所需完成数

前段累计745次完成到29，末级要求陡增。

1 / 30SDK钱包第五段固定进度

该展示没有读取真实玩家等级。

＋结构优点

  • 阶段切换、奖励弹窗、延后与恢复由专门协调器组织。
  • 玩家离开页面后的任务状态可以保存和恢复。

↳主要问题

  • 显示关卡、有效时长和真实统计口径不一致，完成成本难以预估。
  • 最终资格完成后没有创建下一待执行流程；领取关闭钱包后不再推进。
  • 记录页只追到关闭绑定，没有完整的列表填充。
读对这一点

“极难达到30级”和“后台绝对达不到30级”不同。这里还必须单独检查最终领取的执行链。

查看代码依据与结论边界＋
F-HM-001PhaseTaskService / 任务配置

首段显示8关，实际要求40关；有效活跃还附带分段成功计数条件。

F-HM-002GetSdkProgress / PlayerLevelProgress

第五段展示固定Current=1、Target=30、Normalized=0；真实等级表单独计算。

F-HM-003CandyPanel.OnAction → PhaseFlowCoordinator.RunFlow

最终完成不创建pendingFlow；没有待执行流程时返回，记录页未形成完整列表。

设计判断 · 非经营实测

前期阶段反馈具备连续结构；后期任务量增长明显，但不能由流程长度推定长期留存或回本。

CASE / 02
进度转收集型已分析版本 1.6

Solitaire Money Tree

100%之后，还有一套字母收集条件。

前段按关卡增加提现进度，达到100%后出现FINAL STEP，继续要求收集G/R/E/A/T。

机制路径以当前已追踪流程为准
  1. 关卡进度
  2. 51级到100%
  3. GREAT收集
  4. A权重为0
  5. 最终领取未闭合
51达到100%的玩家等级

50级为99.99%，51级为100%。

5 / 4 / 3 / 0 / 1G / R / E / A / T权重

正权重累计算法不会选中第四项A。

10Money Garden植物种类

牌局、种树、签到和转盘共同提供显示余额反馈。

＋结构优点

  • 牌局与植物产出、升级提供多种可操作的成长来源。
  • 重复字母有明确的显示现金补偿，奖励分支可追踪。

↳主要问题

  • 进度100%与整个提现流程完成不是同一含义，之后继续出现条件。
  • 已追踪关卡结算源中A权重为0，已追踪签到/转盘也不提供字母。
  • 历史受控五字母全亮时CLAIM仍灰；最终页未找到完整领取提交链。
读对这一点

100%本身可以达到。问题在后置收集及最终领取页，不能概括为“进度永远到不了100%”。

查看代码依据与结论边界＋
F-SMT-001FetchJIndu / FinalMoveView

playerLevel50为9999/10000，51为10000/10000；之后进入GREAT收集页。

F-SMT-002RoundWinView → FetchWeightSlot

Z1..Z5对应G/R/E/A/T，权重[5,4,3,0,1]；结论限定已追踪本地奖励源。

F-SMT-003FinalMoveView.Start / RebuildView

已追踪最终页负责显示和关闭；五字母全true是反事实受控状态，不是自然收集证明。

设计判断 · 非经营实测

前期成长内容来源较多；收集本可承载中期目标，但当前选择路径与最终按钮没有形成可完成的闭环。

CASE / 03
多分支订单型已分析版本 1.0.2

Rings Cash

现金、碎片、实物转盘三条线并行。

现金订单叠加关卡、广告、跨日任务与等待；手机碎片和独立实物转盘另有订单与物流流程。

机制路径以当前已追踪流程为准
  1. 20 / 30关入口
  2. 金额与VIP
  3. 多轮任务 / 等待
  4. 7952人队列
  5. 仅刷新数字
03相互独立的主要分支

现金订单、手机17碎片、独立实物转盘。

0 人现金队列仍停原阶段

归零后队列刷新只更新文本，没有结算迁移。

43 天US本地物流表末节点

61920分钟，末节点为地址错误退回，另有保存的秒级偏移。

＋结构优点

  • 不同类型目标拥有各自的状态、入口与记录。
  • 奖项目录、地区和物流配置可以通过参数化结构复用。

↳主要问题

  • 账号、VIP、补偿、广告计数、日期和多套订单交叉，理解和维护成本高。
  • 现金队列降到0后仍在stage6，不推进为付款完成。
  • 两套实物分支读取本地物流表，当前53地区表均以地址错误退回结束。
读对这一点

手机碎片并非永久卡90。超过90后的部分限制按日期判断，次日广告仍能补到100；需要继续看下游订单。

查看代码依据与结论边界＋
F-RC-001GameController / 订单阶段回调

同一版本因福利与Enhanced状态显示20或30关入口；后续叠加金额、关卡、广告和时间条件。

F-RC-002WithdrawalQueueAhead / RefreshOrderQueue

max(0,7952-floor(elapsed_ms/600000))；刷新只改文本，归零不触发完成。

F-RC-003PrizeFragmentLedger / 碎片广告限制

超过90后地图停止，部分广告限制在次日解除，目标100仍可达到。

F-RC-004 / 005PrizeDeliveryCatalog / LuckyLotteryShippingTimeline

实物状态由本地提交时间、地区和包内时间表选择；独立转盘还有SIM/GAID可用性门控。

设计判断 · 非经营实测

多分支承载了多种目标与较长等待，但查看订单和物流不等同于对核心玩法的长期兴趣。

CASE / 04
审核与储蓄型已分析版本 1.0.3

Smash Cash

奖励逐段减小，审核停在待付款。

普通提现采用国家档位和递减奖励，提交后经过三段审核；利息/储蓄拥有另一套任务与记录。

机制路径以当前已追踪流程为准
  1. 分档累计金额
  2. 提交申请
  3. 三段审核
  4. stage 3
  5. 已批准 / 等待付款
0–0.01US最后段普通奖励范围

>=999.5后仍允许正数，允许0不等于每次必为0。

stage 3普通审核函数终点

达到该阶段后不再推进，显示等待付款。

04独立利息 / 储蓄任务

奖励次数100、储蓄广告30、US余额目标170、登录7天。

＋结构优点

  • 国家档位、奖励区间和审核记录采用配置与数据结构组织。
  • 普通提现与利息/储蓄可以分开追踪状态和提交记录。

↳主要问题

  • 审核结束没有接入已追踪路径中的资金完成状态。
  • 审核每次检查重新抽当前阶段的时间阈值，完成时间不易形成稳定预期。
  • 利息提交写入InProgress并保存金额、日期，付款展示不能当作转账完成。
读对这一点

不能仅凭最后奖励段允许0，就断言数学上永远攒不到1000。更明确的代码终点是审核停在待付款。

查看代码依据与结论边界＋
F-SC-001 / 002WithdrawalSubmissionData.AdvanceReview

三组阈值[12,24)、[24,48)、[48,72)小时；reviewStage>=3不再推进。

F-SC-003PureRewardPolicy / SubmitPurePiggyWithdrawal

独立四段任务后写InProgress记录；显示付款阶段与实际付款分开。

来源：奖励策略配置PureRewardPolicy / 国家奖励配置

US末段>=999.5的普通奖励允许0–0.01；不能把随机区间中的0理解为恒定0。

设计判断 · 非经营实测

递减奖励改变接近目标时的反馈节奏；储蓄提供副线，但等待审核本身不代表持续参与。

CASE / 05
多口径等级型已分析版本 1.0.4

Pixel Sand Puzzle

显示关、有效时长和玩家等级各算一套。

短关卡目标后追加在线、48小时、银行审核与等级条件；最终目标超出当前等级函数的返回范围。

机制路径以当前已追踪流程为准
  1. 显示5关
  2. 实际16局
  3. 在线 / 48h审核
  4. 要求玩家30级
  5. 函数最高返回28
5 → 16显示关 / 实际关卡数

完成前5个显示关合计需要16个原始关卡。

× 0.7有效在线时长折算

计入20分钟约需28分35秒实际有效活跃。

30 / 28最终要求 / 当前最高返回

结论限定当前生效等级表与函数组合。

＋结构优点

  • 关卡、在线、签到和申请状态具备配置与记录载体。
  • 能够通过配置和调用关系追溯各进度口径的来源。

↳主要问题

  • 多套进度和折算时长使玩家难估计真实达标成本。
  • 当前GetCurrentUserLv最高返回28，最终要求30，不只是升级速度慢。
  • 排队的9812人/8632位是本地语言文案；签到后四档还依赖同一30级条件。
读对这一点

这里是当前等级返回域无法满足目标。配置中的0.01与页面成功都不代表已取得真实小额支付证明。

查看代码依据与结论边界＋
F-PSP-001 / 002GetShowLevel / 关卡映射表

前5个显示关对应16个原始关卡，不能把显示关数当实际局数。

F-PSP-003PlayerLvManager.GetCurrentUserLv / 当前有效等级表

29与30级阈值相同，首个大于进度的条目返回Level-1，遍历耗尽返回1；最高返回28。

F-PSP-004 / 005语言ID135 / SigninManager.IsFinishTotalCondition

队列人数和位置直接写在文案；后四档签到要求玩家30级，Real_Value配置为0。

设计判断 · 非经营实测

早期目标表达较短，后续转向在线和等级；当前末端条件不可由该等级函数满足，无法形成完整达成闭环。

CASE / 06
多阶段资格型已分析版本 1.0.0

Crazy Water Puzzle

小额记录之后，继续转向余额、有效打卡与等级。

九段主阶段和独立引导共同控制页面：前段US小额配置与本地成功记录，后段追加隐藏关、动态余额、有效日期和等级条件。

取证范围：本轮仅静态代码与包内配置分析；未启动游戏、跑广告或验证真实付款。

机制路径以当前已追踪流程为准
  1. 小额配置 / 记录
  2. 隐藏关与余额目标
  3. 5个有效打卡日
  4. 最终等级资格
  5. 包内返回域不满足
0.18 / 0.24前两段US金额配置

对应Condition_1=1/2；本地成功记录不代表实际小额付款。

5天 × 10关有效打卡日数 / US日门槛

有效日计入仅在Step6/7，按本地日期当天计一次，不是纯登录。

>30 / 28资格完成判断 / 包内最高返回

UserMaxLv=30，完成判断用严格大于；结论限定包内表与原函数。

＋结构优点

  • 阶段、国家参数与本地记录可分别追踪，便于定位每个条件的来源。
  • 主按钮通过异步路由切换金额、打卡、等级和处理说明页。

↳主要问题

  • 显示关、藏关表与全局计数还有减3偏移，单看显示目标难估实际成本。
  • 等级页面目标30，但完成谓词是>30；包内等级表和原函数最高返回28。
  • 确认回调先写本地isTx成功标记再显示成功页，尚无真实资金回执。
  • 主面板提现提示使用本地随机用户名、渠道和配置金额，不能代表真实他人收款。
读对这一点

小额配置、成功标记和奖励提示不是支付平台确认。最终还要分清“显示达到30”与代码要求“严格大于30”。

查看代码依据与结论边界＋
F-CW-001GetEMergeSortStep / StepConfig / GameLoginDayManager

Step1..9分段推进；构造值MaxLoginDay=5，US日关卡门槛10；有效日期只在对应阶段且关卡计数满足时增加。

F-CW-002GetUserLv 0xEC7CA8 → GetIsFinishGameLevel 0xEDF2D0

首个更大阈值返回lv-1，耗尽返回1；29/30阈值同为1000002804，最大返回28。UserMaxLv30而完成谓词>30。

F-CW-003Confirm.MoveNext / SetTakeOutLogData / WaterRewardPrompt

确认回调置isTx=true并写本地PlayerPrefs后推成功页；Java showRewardConfirmation只是本地Toast，不是资金确认。

F-CW-004SetNoticeData → RandomChannel / GetUserName / GetDMDanmuValue

名字由两个列表随机组合，提示金额来自包内区间。结论限定此提示构造，不能作为真实他人提现证明。

设计判断 · 非经营实测

前段反馈之后，后段要求余额、有效日期和等级；能够描述条件怎样延长，但缺该包的实际收益与留存数据，不能推定已回本。
